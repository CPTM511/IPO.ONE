## 4. 建议的产品组织

已确认：任务优先，并保留账户摘要和可直接访问的总览。

- 登录后首先显示当前状态、最需要处理的一件事、关键金额/期限以及最近结果。已经有账户的用户恢复到服务端确定的工作进度。
- Human 主导航建议为“下一步 / 我的信用 / 动态 / 设置”；Agent、Capital Partner、Provider、Risk 使用各自任务语言和实际授权入口。
- 常用入口约四项，其余能力通过明确分组及上下文链接到达。全量可达性盘点覆盖每个角色允许的页面。未开放能力显示原因和恢复条件，不占据主要行动位置。
- 切换 Human、Principal、Agent 或其他工作区，只改变已获授权的上下文，不授予角色或权限。
- 账户、会话、环境和网络信息集中呈现；必要边界持续清楚，详细协议说明按需展开。
- 内部 ID、哈希和操作名保留在可查询详情中，不作为普通用户完成流程的前提。

## 5. 需要贯通的任务

| 范围 | 用户应能完成的事情 |
| --- | --- |
| 进入与恢复 | 官网进入 → 使用当前环境真实可用的已批准认证 → 首次引导或恢复工作台 → 退出与重新登录；保留进入前的合法目的地 |
| Human | 身份与 Consent → 请求 → 解释与条款比较 → 明确接受 → Obligation/许可使用 → 还款计划 → 结果与 Evidence；异常有恢复路径 |
| Principal / Agent | 识别下一位责任人 → 完成已有绑定/接入 → 明确授权范围 → 运行已授权任务 → 查看步骤、等待原因、结果和记录；暂停/撤销仅通过现有合法能力 |
| Capital Partner | 授权请求收件箱 → 审查 → 已有 Offer 操作 → 交接与组合跟踪 → 还款/异常/Evidence |
| Provider / Risk / Operations | 角色允许的待办与异常 → 上下文 → 明确操作 → 可查询结果；保留双人复核等已有规则 |
| 全局 | Activity、Credit Passport、报告、权限、集成及所有已批准可用产品视图具备入口；M2/M3 等按当前环境与能力状态呈现 |

Human 与 Agent 使用同一内核。Agent 验收包含实际授权 API/MCP 与回执，不能用浏览器中的模拟运行替代机器端流程。未实现的领域行为先与能力登记核对并单独列项，不能为了展示顺畅伪造完成状态。

## 6. 交互与视觉主张

- 官网保留大胆、有表现力的 Fintech 方向；内部以清晰的金额、条款、授权和进度为视觉中心，避免每页重复宣传首屏。
- 一页一个占主导的当前动作；重要确认显示操作对象、金额、影响和结果，按钮名称表达实际动作。
- 系统自动完成已允许的读取、恢复、预填与校验。需要 Consent、授权、接受或付款的决定保留明确控制；已获精确授权的 Agent 工作不重复索取无意义的逐步确认。
- 动效解释对象关系与状态变化，操作后立即有反馈；用户输入可中断过渡，业务成功只能由服务端结果决定。
- 覆盖等待、成功、拒绝、失败、未知、空状态、过期、会话失效；保留输入并提供合法恢复方式，不强迫盲目重试。
- Light/System/Dark、桌面/中间宽度/手机统一质量；检查焦点、键盘、200% 缩放和 reduced motion。手机按任务重新排布，金额、条款和当前动作优先。

## 7. 建议交付顺序与验收

这不是一次性全站重写。Alignment 确定后才生成总指令和顺序执行的独立任务，任务应映射已有任务与当前能力，逐项写明范围、非目标、文件、验收、测试、权限、迁移影响、回退与证据。

1. 当前功能/入口/角色/真实宿主盘点，确认代码基线；区分样式、接线、配置与领域能力缺口。
2. 登录、首次进入、退出恢复与公共应用框架；在现有批准配置内连接实际服务。
3. Human 完整路径与 Principal/Agent 完整路径，应用相同的组件和状态语言。
4. Capital Partner、Provider、Risk 及剩余角色页面，全站可达性、异常、手机和主题覆盖。
5. 在确定版本上完成浏览器与服务验证，提供持续可访问的本地候选；需要上线的批次另明确部署审查与实际部署版本验收。

每批以用户任务验收：从可见入口开始，不手填内部 ID；结果能再次查到；刷新、重新登录和适用的进程重启恢复一致；拒绝或未知不会显示成功，也不因重复点击重复提交。视觉回归必须覆盖中间宽度与实际长文本，不能仅靠无横向溢出判断布局正常。

使用测试数据可辅助布局和回归，但最终产品可用性需要真实认证、服务端操作及持久化证据。CODE、RUNTIME、DEPLOYED、REACHABLE、VERIFIED 分别记录；本地候选不能称为已部署且已验收产品。
