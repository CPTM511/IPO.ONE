## 1. 目标：让专业性体现在每一次操作里

用户希望：**更大胆、更有展示张力，同时细节精致；关键产品场景有明显表现力，操作始终清楚、可控，有科技感与 Fintech 感。**

将这些要求转化为五个可检查的结果：

1. **对象明确。** 首屏能识别当前身份、Agent / 信用计划 / 待处理事项，以及实际状态。进入 Agent 页面不能再被 Human profile 和还款引导占据主区域。
2. **决策集中。** 关键金额、用途、期限、限制和操作结果形成视觉中心；每页最多一个视觉上占主导的主动作。
3. **视觉有辨识度。** 石墨色工作面、精准数字排版、薄荷色重点、稳定操作区共同形成 IPO.ONE 内部产品语言。通过比例、秩序和细节建立质感。
4. **交互有连续性。** 用户始终知道刚做了什么、系统正在做什么、下一步是什么；切换、加载、失败和返回都有明确反馈。
5. **完整且真实。** 登录、权限内的流程、明细、异常、历史记录和恢复路径均可使用。视觉完成不能掩盖服务、权限或持久化缺口。

## 5. 关键流程与状态设计

### 5.1 登录必须闭环

保留并回归 WEB-026H 修复。用户看到的过程必须区分：连接钱包、等待签名、服务端核验、进入工作区。连接成功不是登录成功，完成签名也不是服务端已经接受。

- 服务端建立有效会话后自动进入对应工作区；不再要求额外点击 Continue 才能进入。
- 取消、拒签、超时、账户切换、网络错误、过期会话和错误角色均有准确反馈及恢复入口。
- 刷新、退出重登、合法会话恢复后从服务端重建身份和下一步；不依赖前端缓存伪造已登录。
- 核对本地与正式认证配置差异。不得把 WEB-026H 的本地专用自助注册开关、测试钱包、密钥或 fixture 带入正式配置；保持正式 canonical 认证模式。

### 5.2 Agent 样板场景

以“首次进入 → 接入/选择 Agent → 审阅授权 → 明确授权 → 查询结果和 Activity”建立第一条完整样板。

首次进入展示真实准备状态与下一步，不渲染一排无意义的 `—` 指标。审阅时明确显示：谁授权给谁、用途、适用 Provider、额度及币种、单次限制、期限、不可执行范围、授权后会改变什么。

拟定、等待、已授权、暂停、过期和失败必须可区分。右侧操作区保持稳定，金额、作用对象和后果靠近主按钮。名称、排序与可选项均来自已有产品模型。若真实模型比概念图复杂，使用分组和渐进展开，不隐藏必需步骤。

### 5.3 Human 与其他角色

Human 的申请与 Offer 决策使用同样清楚的金额、期限和后果表达；明确区分查看 Offer 与接受后建立 Obligation。还款/处理结果能进入记录核验。

Capital / Risk 工作区优先显示待处理项、优先级与判断依据；选择对象后才展开明细和决策区。批量操作、筛选或自动刷新不得改变授权语义。仅实现服务端已有且当前角色被允许的操作。

### 5.4 全站状态合同

对每个重要组件与流程覆盖：首次空状态、正常数据、加载、提交中、成功、校验失败、服务错误、无权限、未配置、过期/陈旧、结果未知。只覆盖实际适用状态，不编造领域不存在的状态。

- 空状态解释原因并给出安全下一步；有无数据均应有完整设计。
- 用户输入在可恢复错误后保留；字段错误靠近字段，整体错误说明可执行的恢复方式。
- 提交中防止重复操作；成功由服务端回执驱动。请求超时但结果未知时，先查询/对账，不用动画宣告成功，不盲目重试经济或授权变更。
- Back、Next、View、Open 等导航文案不能隐藏 mutation。重要按钮命名对象和后果；确认展示实际金额、目标、条款、权限与运行模式。
- 列表进入明细再返回时合理保留筛选、排序和位置；浏览器前进/后退、刷新及深链接需正确恢复。
- 技术 ID、hash、schema、request ID 留在可展开的技术回执里；正常操作不要求复制内部标识。

## 6. 动效、响应式与可访问性

动效用于解释状态和空间关系。Hover / press 可从 120–160ms、面板转换 180–240ms、结果过渡 220–320ms 开始验证；这些是设计起始值，不是实测竞品指标或业务响应承诺。

- 控件收到操作后及时进入 pending 状态；真实长任务显示实际阶段或等待说明，不用虚构百分比。
- 决策按钮、关键金额和当前选择在异步更新时保持位置稳定。禁止持续脉冲、价格假跳动、粒子、无意义光晕和影响阅读的全屏转场。
- 支持 `prefers-reduced-motion`；不依赖动效或颜色单独表达状态。
- 验证桌面 1440×1024、中间宽度 1024、平板 768、手机 390 和窄屏 320，以及 200% 缩放。按内容决定断点，不以设备名硬套布局。
- 窄屏先展示对象与条款，再展示决策；抽屉和粘性操作区不得遮住关键内容、键盘焦点或错误信息。
- 键盘可到达全部主要操作；焦点可见、顺序合理。对话框有焦点管理、关闭与返回位置；动态反馈可被辅助技术获知。
- 检查正文/元信息、按钮、禁用原因、边界与焦点的实际对比度，按项目采用的无障碍标准验收。金额与单位、长名称、长错误信息均不得被关键裁切。
- 保持现有支持语言；避免同一流程中术语混乱。本次不默认为建立一套全新国际化平台。

- 避免重写框架、复制后端、引入第二套状态真相，或另建一个无法接入现有服务的展示站。

- 保留 Human UI 与已有版本化 API / MCP 对同一协议的等价能力。本次 UI 优化不得改变 kernel、ledger、risk 或协议语义。
- 不因视觉需求新增生产依赖、动画引擎、外部字体/追踪服务；确需新增时说明收益、成本及相应审阅边界。先测量再优化资源加载和长列表，避免不必要的新请求及重复渲染。
- 设计阶段可用明确标注的隔离 synthetic data；最终功能验收使用实际候选服务和持久化隔离测试数据。禁止前端硬编码成功作为交付。
- 自行选择有实际作用的 skills / MCP。优先相关产品设计审视、选定图实现、浏览器验证及现有发布工具；先读对应 skill。Figma 仅在能改善本次设计系统时使用，ImageGen 仅用于确有需要的视觉资产。不要为用工具而重新生成三套方向或另建托管项目。
- 对正式账号、钱包签名和权限确认保持清楚操作边界；自动化验证使用获准的隔离测试身份，不替用户签署未授权的业务操作。

## 8. 分批任务与推进方式

建立 WEB-027 父任务及以下子任务文档。每项写明 context、scope、non-goals、likely files、acceptance criteria、test command、security checklist、permission boundary、migration impact、rollback 与 completion evidence。逐项推进，每项完成后更新矩阵，不将整个程序塞进一个无法审查的大提交。

## 9. 验收与回归要求

### 9.1 视觉验收

把所选概念与实现放在同一比较视图里，对齐近似视口、同类内容及相同状态检查；明确列出为真实产品、响应式或可访问性作出的有意调整。不要用不同数据、不同滚动位置掩盖布局偏差。

至少验证：信息主次、字体与字重、数字和列对齐、间距、边界、颜色、首屏密度、右侧操作区、长文案、空状态、错误、窄屏和 Light。截图可证明画面，不能代替操作验证。

### 9.2 用户流程与真实状态

- 从可见公开入口进入登录，并通过正常操作到达角色工作区。
- Human 和 Principal 完成适用核心旅程；涉及授权或生命周期改变的步骤用清楚控件执行并查看结果。
- 其他纳入范围的角色使用合法已授权身份验证。无可用身份或环境时，记录对应项为未验证/阻塞，不用前端切换角色证明通过。
- 全部角色允许视图经可见入口到达；校验旧链接兼容、前进/后退、刷新和退出重登。
- 关键状态在刷新、重登和候选进程重启后恢复；改动涉及 worker、事件、数据层时，额外验证重放、重复事件及数据库恢复的适用边界。
- 钱包取消/拒签、过期、撤销、重复提交、错误角色、身份隔离、对象访问和会话恢复无回归。保留已有安全测试，不通过削弱断言获得绿色结果。
- 无数据、慢请求、断网、服务异常、陈旧状态及结果未知都有可恢复反馈；成功提示能对应可查询回执。

## 10. 交付边界

本次包括：全站视觉与交互系统、信息组织、已有可用功能的操作体验、正确服务集成，以及为本范围所需的最小普通缺陷修复。保留 Human / Agent shared kernel、现有 API/MCP 合同、数据隔离和角色模型。

本次不自动批准：新金融产品、风险/额度/定价规则、合约与 signer、资金流、mainnet、外部 Provider、KYC/隐私边界、生产依赖、身份/权限扩展、破坏性数据库变更或新的部署拓扑。已批准 profile 的准确权限以 canonical policy 为准。出现这些需求时提供独立具体方案，不能借“全站优化”顺带实施。

未实现或受限能力应真实可理解；有权查看的能力不应无故消失。对于范围内仍被依赖阻塞的旅程，继续完成其他可验证工作，保留明确状态。不得悄悄缩小全站承诺，也不得把一个局部完整候选称为全站完成；若需要先发布子集，应具体列明差异并取得范围确认。

## 11. 本地、正式发布与回滚

### 11.1 本地候选

先在隔离的候选运行环境验证，再按现有本地运行手册提供稳定体验；保留原可用版本和数据恢复方案。不要关闭其他任务的服务、重置当前体验数据，或在尚未验证时覆盖用户正在看的版本。

每次交付给 Founder 都提供可点击且实际可达的产品链接，说明角色、候选版本和运行模式。保持服务在本地评审期间可用；PR、截图、代码路径和日志不能替代产品链接。

完成本地测试后，提交简短变更说明、样板与全站截图、剩余问题、测试证据和具体体验路径，供 Founder 确认视觉与操作结果。没有反馈不能自行视作体验确认。

### 11.2 进入正式发布的条件

以下条件全部满足后，在已批准范围内继续发布，不再重复索取同一范围的概括许可：

1. Founder 已确认本指令；本地候选符合已确认的方向，Founder 已体验确认。
2. 本次范围和所有关键回归通过；没有未解决的登录、角色、关键操作、数据恢复或明显布局阻塞。
3. 已确定包含最新必要修复的目标提交、可复现构建、候选部署方式和正式目标；不能凭本地截图替代版本绑定。
4. 已核对环境差异，沿用现有正式拓扑及当前获批产品模式；无本地测试开关、fixture、私密配置或测试身份泄漏。
5. 发布记录列出影响面、测试、配置/迁移影响及可执行回滚步骤；当前 required checks 和适用 launch gate 满足。

先理解仓库 push / merge 与自动发布的关系，再按已有分支、PR、预览及推广流程操作。正式地址从现有部署配置和域名映射核实，不重新创建托管项目。依赖不可用、必须新增权限或超出已批准范围时，说明具体阻塞和可审阅方案。

### 11.3 正式复验与失败处理

- 在实际正式域名核对部署 ID、源 SHA、构建产物及资源版本，避免页面 shell 更新而旧 JS/CSS 仍在缓存。
- 使用获准身份，从可见入口复验正式环境登录、核心旅程、导航、状态恢复和适用角色。正式测试数据遵循当前环境规定，不能把本地 QA 凭据复制上线。
- 验证本地与正式环境差异相关路径，尤其是钱包认证和服务端身份恢复。不能把本地通过推定为正式通过。
- 出现登录不可用、授权异常、数据完整性问题、关键路径失败或严重布局破坏时，按已准备的流程回滚到上一兼容版本；保留当前数据并再次验证可达性，禁止用清空数据恢复表面正常。
- 发布后提供正式产品链接与简短变化说明。最终验收针对实际部署 SHA；若由 Founder 完成特定账号验证，明确记录该待办，不能代其宣布通过。
